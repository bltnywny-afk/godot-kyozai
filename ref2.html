Gitとgithubの使い方

この付録のねらい：変更を安全に記録し、GitHubで公開する一連の流れを覚える。

Gitは「ファイルの変更履歴を記録する道具」、GitHubは「その履歴をネット上に置いて、公開したり他の端末と共有したりする場所」です。このサイト自体も、Gitで記録してGitHubで公開しています。

状態がどう変わるか

ボタンを順に押して、1つのファイルの変更が「作業ディレクトリ → ステージ → ローカルリポジトリ → GitHub」の4か所をどう移っていくか見てください。押した段階までしか色が付かない＝その先にはまだ変更が届いていない、という意味です。

出てくる言葉

言葉意味
リポジトリ変更履歴ごと管理されているフォルダ
ステージ次のコミットに含める変更を、仮に置いておく場所
コミット「ここまでの変更」を1つの記録として保存すること
プッシュ手元の記録をGitHub（リモート）へ送ること
プルGitHub側の記録を手元へ取り込むこと
リモートGitHubなど、ネット上にあるリポジトリの置き場所
ブランチ本流から分かれて作業できる並行の履歴
クローンGitHub上のリポジトリを手元にまるごと複製すること

基本の3手順

ファイルを変更したら、次の3つを順に行います。

git status          # 何が変わったか確認する
git add .           # 変更をコミットの対象に含める
git commit -m "説明" # 変更を1つの記録として保存する

git statusは変更されたファイルの一覧を教えてくれます。何が起きるか分からないときは、まずこれを打つ癖をつけておくと安心です。-mのあとの説明は「何を・なぜ変えたか」を短く書きます。あとで履歴を見返したときに、ここだけが手がかりになります。

GitHubへ公開する

コミットは手元のパソコンの中だけの記録です。GitHub上に置いてあるリポジトリへ送るには、もう1手順必要です。

git push            # 手元のコミットをGitHubへ送る

このサイトはGitHub Pagesという仕組みで公開されているので、git pushが終わると、1〜3分ほどで公開ページにも同じ内容が反映されます。逆に言うと、コミットしただけ・pushし忘れた変更は、公開ページには一切反映されません。

ここで確認

変更後にgit statusを打って「何も表示されない（nothing to commit）」なら、コミットまで済んでいる。さらに手元とGitHubの内容を揃えたいなら、pushまで行う。

いつコミットするか

「1コミット1目的」が基本です。1つの回の追加、1つの誤字修正、1つの機能変更、というように、あとから見て意味のかたまりが分かる単位で区切ります。1回の変更にいろいろな用件を詰め込むと、あとで「どの変更が原因か」を追えなくなります。

やってしまいがちな詰まりどころ

変更したのに公開に反映されない

ほとんどの場合、git commitまでで止まっていてgit pushを忘れています。git statusで確認し、git log --onelineで直近のコミットが並んでいるかも見ておくと分かりやすいです。

コミットメッセージを書かずに止まる

git commitだけ打つとエディタが開いて操作に迷うことがあります。git commit -m "説明"のように-mで直接書いてしまうのが簡単です。

やってみる

このサイトのどこか（誤字でもよい）を少し直し、git status→git add .→git commit -m "説明"→git pushの順に打ってみる。数分待ってから公開ページを開き、直った内容が反映されているか確かめる。
